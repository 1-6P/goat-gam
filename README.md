# 발표자료

## 🔍 **프로젝트명: 곧감 (goatgam)**

---

### ✔️ **프로젝트 소개**

곧감(GoatGam)은 음식 주문과 배달을 효율적으로 관리하기 위한 백엔드 중심 서비스로, 사용자·주문·결제·주소 등 핵심 도메인을 중심으로 설계되었습니다. Spring Boot와 **PostgreSQL** 기반으로 개발되었으며, **JWT 인증**을 통해 보안성을 강화했습니다. 배포는 **GitHub Actions**를 활용해 EC2에 자동화했으며, Dockerfile을 이용한 컨테이너 빌드로 일관된 실행 환경을 유지했습니다. 별도의 Nginx나 HTTPS 없이 **EC2 인바운드 규칙을 활용한 접근 제어**로 단순하고 가벼운 인프라 구조를 구성했습니다. 곧감은 “곧 간다”는 이름처럼, 빠르고 정확한 주문 처리를 목표로 하는 경량형 주문 관리 서비스로, 고객과 사장님을 연결해 식당/메뉴 조회, 장바구니, 주문/결제, 리뷰, 팔로우, 주소 관리, AI를 이용한 메뉴 설명 지원 등 다양한 기능을 제공합니다.

---

### ⚙️ **구현 사항**

- Github Actions와 AWS EC2로 배포, 배포 자동화
- Jwt와 Spring Security를 통해 사용자 구별, 인증 / 인가 구현
- 법정동코드 csv파일을 시도 / 시군구 / 법정동으로 계층화
- API,DB 명세서 기반으로 MVP 및 추가 기능 구현 완료.

    ```
    - 인증/인가: JWT 기반 로그인/회원가입, Spring Security 필터 구성
    - 주소 관리: 법정동 주소 데이터 연동(옵션 CSV 로더), 사용자 주소 연결
    - 식당/메뉴: 조회, 검색, 페이징, 사장님 전용 식당/메뉴 관리
    - 장바구니: 담기/수정/삭제 및 합계 계산
    - 주문/결제: 주문 생성/상태 관리, 결제 모듈 연동 구조
    - 리뷰/팔로우: 가게 리뷰 작성/조회, 팔로우 기반 피드
    - AI: Google Gemini API를 활용한 메뉴 설명 작성
    ```

### 🧩 **기술 스택**

- **Backend**: Java 17, Springboot 3.5.6
- **Infra/CI**: Docker, Github Actions, AWS EC2
- **Database**: PostgreSQL
- **Test** : mockito + JUnit: 5.11.0 , Swagger 2.8.9

---

### ✔️ **기술 선정 이유**

- **Github Actions**: 쉽게 배포 자동화가 가능하고 팀에서 사용하는 형상 관리 툴인 GitHub에서 편하게 관리할 수 있다.
- **Springboot**: 애플리케이션의 요구 사항에 맞게 자동으로 설정을 적용하고 스타터 패키지가 있어 개발 생산성이 향상된다.
- **Docker**: 개발 및 배포 과정을 간소화하고, 격리된 환경에서 테스트 할 수 있어 시스템 전체에 미치는 영향을 줄일 수 있다.
- **PostgreSQL**: 무료로 제공되는 DB 서비스이며 안정성과 확장성이 뛰어나다.
- **Github issue** : 코드 충돌 (Conflict) 을 최소화하여 효율적인 협업이 가능하다. 코드를 서로 리뷰하여 오류사항을 쉽게 수정하거나, 업데이트한 부분에 대해서만 쉽게 질문할 수 있다.
- **RestClient:** RestTemplate은 deprecated 예정으로 확장성과 유지보수가 어렵기 때문에, Spring MVC 환경에서 별도 의존성 없이 간결하고 예외 처리가 용이한 RestClient를 사용하며, 현재 트래픽 규모와 아키텍처 특성상 비동기인 WebClient 보다 RestClient가 적합하다.

3. 해결 방안

   : `CustomAccessDeniedHandler` 생성, 팀 전체의 핸들러 작성으로 이제는 삭제

4. 결과

   : 

    ```jsx
    {
      "status": 403,

      "message": "접근 권한이 없습니다.",
      "path": "/api/v1/user"
    }
    ```

<aside>

1. 문제

   : POST `/api/orders` 호출 시 다음과 같은 에러들이 순차적으로 발생

    1. `HttpMediaTypeNotAcceptableException: No acceptable representation`
    2. `HttpMessageNotReadableException: Required request body is missing`
    3. `SQLState 23502: null value in column "price" violates not-null constraint`
2. 원인

   : 1. `OrderSaveResponseDto`에 getter가 없어서 Jackson이 JSON 변환 불가.

    2. `@RequestBody String request` 는 기본적으로 `text/plain` 기대 하지만, 클라이언트가 `application/json` 으로 보냈기 때문에 파싱 불가.

    3. `OrderService` 클래스 전체에 `@Transactional(readOnly = true)` 선언되어 있어서 INSERT, UPDATE가 무시됨

    4. SQL 오류 - 엔티티에서는 `price` 필드 삭제했지만, DB 테이블에 남아있음.

   Hibernate INSERT 시 `price` 미포함 → DB가 NOT NULL 위반.

3. 해결 방안

   : 

    1. DTO를 `record`로 변경
    2. DTO로 바꿔 JSON 파싱하게 함:

        ```java
        public record OrderRequestContentDto(String request) {}
        
        @PostMapping(value = "", consumes = "application/json", produces = "application/json")
        public ResponseEntity<OrderSaveResponseDto> addOrder(
              @AuthenticationPrincipal UserDetailsImpl principal,
              @RequestBody OrderRequestContentDto body) {
            return ResponseEntity.ok(orderService.addOrder(principal.getUser(), body.request()));
        }
        
        ```

    3. 쓰기 메서드에 다시 `@Transactional` 붙여 override
    4. DB 스키마와 엔티티 동기화
4. 결과

   : 

    - `POST /api/orders` 요청 및 응답 정상 작동
    - JSON 직렬화 및 역직렬화 정상
    - DB 트랜잭션 정상 커밋
    - 불필요한 `price` 컬럼 제거 완료
</aside>

<aside>

1. 문제

   : 회원가입 시 SecurityContextHolder가 인증정보를 가져오지 못해 UserDetailsImpl 캐스팅 오류 발생

2. 원인

   : SecurtiyContextHolder는 로그인 된 사용자의 정보를 가져오는데 회원가입은 토큰 인증 없이 접근이 가능한 api이므로 인증 정보를 가져오지 못함. 즉, principal이 “anonymous”의 문자열을 값으로 가져 UserDetailsImpl로 캐스팅 할 수 없음.

3. 해결 방안

   : principal이 UserDetailsImpl의 인스턴스일때만 닉네임을 가져오도록 구현. 회원가입 시 발생하는 anonymouseUser일때는 “SYSTEM”을 반환함.

4. 결과

   : 로그인 하지 않은 유저가 데이터를 생성, 삭제, 수정하면 “SYSTEM”이 created_by, deleted_by, updated_by로 들어가고 로그인 한 유저가 데이터를 생성, 삭제, 수정하면 해당 유저의 닉네임(유니크 키)이 들어감.

1. 문제

   : Cart Entity를 조회할 때 연관된 CartFood와 CartFoodOption 데이터가 삭제된 데이터도 모두 함께 조회되는 오류 발생

2. 원인

   : CartEntity에서 한번에 데이터를 조회하기때문에 CartFood와 CartFoodOption Entity에 조회 조건이 걸리지 않음. 즉, soft delete한 데이터까지 전부 조회됨.

4. 결과

   : is_deleted field가 false인 데이터, 즉 삭제되지 않은 데이터만 조회됨.

1. 문제

   4. 결과

<aside>

프로젝트를 진행하면서  “언제까지 어떤 기능을 완성해보고, 회의하자” 와 같은 방식으로 일정을 명확히 정하고 역할을 분담해 진행했던 점입니다.

- 팀원 모두가 주도적으로 작업을 맡아 개발에 참여했으며, 좋은 분위기 속에서 의견을 자유롭게 주고받았습니다.

  ex) 포팅 메뉴얼(DB 연결법), API (authorize) Token 받는 법 , 서버 DB 컬럼값 타입 변경 공유 등

  ex) DB 컬럼에 대한 의논 → 서버 부하를 줄이기 위해 Join 컬럼을 최소화하고, 데이터 비정규화를 이용했습니다.

- 특히 Pull Request 과정의 코드 리뷰 문화가 잘 정착되어 있었습니다. 단순히 기능이 동작하는지 확인하는 것 뿐만이 아니라 , 코드 구조와 설계 개선까지 논의했습니다.
- Pull Request를 최소한의 인원이 리뷰를 해야 합칠 수 있고, 시간에 따라 너무 길어진 PR을 Merge 할 수 있게 해서, 제약과 유연성을 모두 챙겼습니다.

  ex) `PATCH` 요청에서 `status` 값을 단순히 `false`로 바꾸는 기능의 경우 “@RequestBody(요청 Body 어노테이션)이 꼭 필요할까?”라는 피드백이 나왔고, 이를 반영해 더 간결한 API 구조로 개선했습니다.

- 마일스톤으로 일정을 크게 나누고 그 안에서 이슈와 데일리스크럼을 통해 일정을 관리함으로써 일정을 효율적으로 관리할 수 있었습니다.

### ✔️팀 프로젝트를 진행하며 느낀 점

### 태휘

- 기획 부분이 좀 줄고, 만들어야 할 기능이 정해져 있기 때문에 이슈를 만들어서 하면 추가 이슈 생성은 버그나 핫 픽스에서 사용될 줄 알았지만, 여전히 부족한 것들이 튀어나왔다.
- 팀원 중에 E가 많은 적이 처음인데 신선하고 의견이 많이 나눠진 점이 팀의 장점이라 생각한다.
- 디버깅 할때 인증 / 인가 부분에서 예외처리를 잘 잡지 않으면 403에러만 보인다. 다음 프로젝트를 진행한다면 이 부분을 좀 더 신경써야겠다.
- 팀원들 마다 각각 코딩이 잘되는 시간이 다르고, 그 집중하는 시간들이 Pull Request를 통해서 어느정도 확인 되는게 재밌었다.

### 진현

- ERD 정말 간만에 만들어봤는데 데이터 연결이 너무 어려웠다. 1:1 인줄 알았는데 연결이 될수록 1:N이고 N:M이었어서 너무 헷갈리고 어려웠습니다.
- 프론트엔드 작업을 위주로 하다보니 Spring에 대한 기억이 많이 휘발되었었는데, (응답,요청 DTO 적용이나 Builder 사용 등) 팀원들이 많이 잡아주고 어떻게 하는게 더 낫지 않냐는 의견을 많이 주셔서 감사했다.
- JPA를 팀으로 써본 프로젝트는 처음이었는데, 네이밍 규칙이나, @ManyToOne 등의 관련 어노테이션을 실제로 어떨 때 써야하는지 배울 수 있었다.
- 평소에 너무 시끄러운 편인데 헛소리해도 팀원분들이 잘 받아주셔서 감사했다, 다들 외향적인 성격이셔서 의견 교환도 너무 자유로웠고 처음에도 어색한 분위기 풀어주셔서 정말 감사했음.

### 은선

- 팀 분위기가 다들 적극적으로 스스로 할 일을 찾고 다른 사람의 일을 도와주려고 하는 분위기로 진행돼서 덩달아 열심히 하게되는 점이 좋았습니다.
- 대신 눈 깜빡하면 열정적인 팀원들이 어디선가 할 일을 다들 찾아 진행해서 저도 늘어지지 않으려고 노력하는 긴장감(?)이 있었습니다ㅋㅋㅋ
- 문제가 생기면 다들 말벌아저씨처럼 달려오셔서 아주아주 든든했습니다!!
- 원래 습관처럼 코드를 짜는 경향이 있었는데 이번에는 팀원들이 함께 코드를 리뷰하고 분석해주어서 구현 원리까지 공부하는 경험을 할 수 있었습니다.
- 배포 작업을 해보고 싶었는데 아직 강의를 못 들어서 폐가 될까 나서서 진행하지 못한 점이 아쉬웠습니다. 공부해서 다음에는 꼭! 어필해보겠습니다ㅋㅋㅋㅋ
- 인증/인가 작업도 언젠간 꼭 해보고 싶습니다. 이 부분을 담당한 팀원이 인증/인가를 하루만에 해와서 저는 기가 팍 죽어버렸습니다… 저도 할 수 있겠죠…?

### 규원

- ERD를 설계할 때는 충분한지 않은가 싶었는데 진행하면서 조금씩 수정해야 하는 부분이 생겨서 처음에 더 많이 고민해야겠다고 생각했습니다.
- 백엔드를 이렇게 많은 사람이 맡아서 하는 것이 처음이라 서로 충돌이 생길까 PR 올릴 때 더 긴장됐던 것 같습니다.
- github action을 사용할 때 yml 파일을 제대로 읽어내지 못해서 많은 시간을 소비했는데 결국 파일 위치가 잘못되어 있었어서 앞으로는 이런 것도 꼼꼼히 확인 해야겠다고 생각했습니다.

### 인규

- 프로젝트 기간 동안 올라온 PR에 코드 리뷰를 진행하며 다른 사람의 설계 방식을 보거나 제 코드의 문제를 바로 피드백 받을 수 있었던 부분이 좋았다고 생각합니다.
- 초기 ERD 설계에 꽤 많은 시간을 ERD에 투자했다고 생각하고 개발을 시작했는데 결국 ERD는 한번에 완성하는 게 아니라 추가적인 수정 사항이 계속 생기는걸 보며 설계 단계의 부족한 부분도 많이 느꼇던 것 같습니다.
- 사실 이번 프로젝트를 진행하며 Swagger를 처음 사용해보았는데 이전에 Postman을 켜놓고 하나씩 테스트하느라 시간을 많이 썻는데 Swagger 덕분에 한눈에 API를 확인하고 바로 요청도 날릴 수 있어서 좋았습니다.
- 프론트를 구현하지 않고 백엔드만 단독으로 개발을 진행 해본건 이번이 처음이었는데 API설계의 중요성을 느낄 수 있었던 신선한 경험이었습니다.
- 아직 Security 쪽은 잘 모르지만 다음 프로젝트에서는 인증/인가나 배포 관련 작업에도 도전해보고 싶습니다.
- 팀원 분들이 다들 활발하시고 자신들의 의견을 적극적으로 표현해 주셔서 팀 프로젝트를 무사히 마칠 수 있었던 것 같습니다.

### 현수

- 초반 설계과정의 중요성을 느낄 수 있었으며, 깃허브 협업 과정의 중요성을 깨달을 수 있었습니다.
- 부족한 부분을 팀원 분들이 이끌어 주셨으며, 연휴 기간 개인 일정으로 인해 협업 간 큰 도움이 되지 못한 것 같은 아쉬움이 남았습니다.
- 이어져 기본 API 설계 뿐만 아니라 다른 인증/인가, AWS 등 다른 작업을 경험해 보고 싶은 욕구가 생겼습니다.
- 무엇보다 커뮤니케이션의 중요성을 느꼈습니다. 논의할 사항이 생기면 엄청 단순한 것이라도 서로 대화를 통해 맞춰가는 점이 너무 좋았습니다.
